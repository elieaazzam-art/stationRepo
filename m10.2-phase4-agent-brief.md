## 1. Mission

Implement **Phase 4 — Audio** of milestone M10.2, exactly as specified in
`docs/PLAN-M10.2.md` §4. The goal, in the plan's own words: **"simple sounds
that make events feel real."** The seam already exists — `crates/engine/src/audio.rs`
has the `AudioSink` trait, the `cue_for` event mapping, and the null sink.
This phase gives the cues an actual voice and nothing else.

The five work packages (the plan's own numbering — they are your scope law):

- **§4.1 The backend** — add one audio backend implementing `AudioSink` in
  the client. Choose the smallest dependable option and justify it in an
  ADR; update the architecture-law allow-list **for the client crate only**.
  The choice is pre-made (the owner's, A-100): **rodio**.
- **§4.2 The sounds** — generated procedurally at startup (simple
  synthesized beeps, clicks, thuds, short noise bursts) so no asset
  licensing is needed and the repo stays small. **One distinct sound per
  cue: attack landed, unit lost, unit ready, structure done, resource
  delivery, match ended, command acknowledged, selection click, UI click.**
- **§4.3 The fallback** — if no audio device exists (CI, headless), fall
  back to the `NullAudioSink` silently. **Never crash or block the render
  loop.**
- **§4.4 The controls** — master volume and a mute toggle in settings.
  Rate-limit repeated cues (for example many attacks per tick) so it does
  not become noise.
- **§4.5 The tests** — cue-to-sound mapping, rate-limiting logic, fallback
  path. Log DEBT-011 progress (this phase repays it).

Note the cue list carefully: the first six ride simulation events through
the existing `cue_for`; the last three (**command acknowledged, selection
click, UI click**) are *client-side moments* with no sim event — see §5.2.

## 5. Work packages with the concrete anchors (all verified at the base commit)

### 5.1 §4.1 — the backend (rodio, per A-100)

The seam today (`crates/engine/src/audio.rs`, 175 lines, all
presentation-side): `AudioCue` (six variants: `AttackLanded`, `UnitLost`,
`UnitReady`, `StructureDone`, `Delivery`, `MatchEnded`), the pure
`cue_for(&Event) -> Option<AudioCue>` mapping, `pub trait AudioSink` with
its single `on_events(&mut self, events: &[Event])`, and `NullAudioSink`
(counts the cues it is fed — that counter is the existing evidence
channel). The client wiring: `main.rs:34` (import), `main.rs:326-329`
(the `audio: NullAudioSink` field and its doc comment), `main.rs:468`
(`App::new`), `main.rs:632` (reset on the restart path), `main.rs:2097`
(fed after each step — **keep that order: after the step, from the
presentation layer; FD-9**), `main.rs:2772-2794` (the headless smoke path
constructs and feeds its own `NullAudioSink`), and the evidence line at
`main.rs:2846` ("feedback wiring: N events fed the audio sink (M cues)").

- **Land rodio**: `cargo add rodio -p pandemonium-client` (whatever current
  version resolves on Rust 1.98.1 — record it in the ADR), the allow-list
  amendment (add `"rodio"` to the client entry of `allowed_external()`),
  and `docs/adr/0002-*.md` — one commit, all three pieces, so the
  architecture-law test never sees an unlisted dependency on a green
  commit.
- **The rodio trap (read this twice): the `OutputStream` must be kept
  alive.** `OutputStream::try_default()` returns `(_stream, handle)` —
  dropping the stream stops all sound. Store the stream in your sink
  struct (it lives as long as the `App`), not in a local.
- **Construction with the fallback built in (§4.3 is not a separate
  work item — it is the constructor's other arm):** try the device once
  at startup; on ANY failure (no device, Xvfb, CI, permission), fall back
  to the null path silently — no panic, no stderr spam, one honest line
  in the startup/evidence output. The natural shape: a client-side enum
  (`Audio = Rodio { .. } | Null { .. }`) or `Box<dyn AudioSink>`-plus-a-
  kept-stream field — your call, log it as an assumption. `NullAudioSink`
  stays as the headless/test path regardless.
- **Thread discipline:** `on_events` runs inside the frame loop — it must
  stay cheap. Precompute the PCM buffers at startup (§5.2); per cue, the
  work is "maybe rate-limit, then hand a pre-built source to the sink" —
  no format negotiation, no device re-probing, no allocation storms.
  rodio's mixing happens on cpal's audio thread; the volume is
  `Sink::set_volume` (cheap, call it when settings change, not per frame).

### 5.2 §4.2 — the nine sounds, all synthesized

- The six event cues come from `cue_for` as today — no new event variants,
  no sim changes.
- The three client-side cues (**command acknowledged**, **selection
  click**, **UI click**) have no sim event. Add a direct-cue path: e.g.
  extend `AudioSink` with `on_cue(&mut self, cue: AudioCue)` (and add the
  three variants to `AudioCue` — the enum lives in engine's audio seam,
  which is presentation-side and yours to grow), with `NullAudioSink`
  counting them for evidence. Trigger points, all client-side:
  a submitted order (the orders layer's success path — decide whether
  "acknowledged" means submitted or non-rejected, log the choice),
  a selection change, and a menu row/button activation (the screens
  machine's activation effect is the natural hook). Log the design as an
  assumption.
- **Synthesis:** pure Rust at startup — beeps (sine/triangle blips),
  clicks (short step/noise bursts), thuds (low sine with fast decay),
  noise bursts (filtered noise) — small mono buffers (well under a second
  each), a fixed sample rate you pick once and log (e.g. 22050 or 44100
  Hz). Nine cues, each **audibly distinct** — that is the plan's letter
  ("one distinct sound per cue"). No asset files, no licensing, the repo
  stays small. Build it as a pure module (e.g. `client/src/sound.rs`)
  following the Phase 2/3 precedent (`silhouette.rs`, `config.rs`,
  `screens.rs`): self-contained, `#[cfg(test)]` tests inside, thin wiring.
- Keep the DEBT-13 discipline: do not grow the `main.rs` monolith — the
  synthesis, the cue table, and the rate limiter all live in the new
  module.

### 5.3 §4.4 — volume, mute, rate limiting

- **Master volume already exists** — wire it live: `config.rs` key 5 of 7
  (`master_volume: f32`, default 1.0, clamped 0.0..=1.0, ±0.05 per
  adjust step at `config.rs`'s `adjust_setting` row 4; the live-apply
  hook is `main.rs::adjust_setting` — row 4 currently falls through to
  `_ => {}` with the comment "Master volume stores for Phase 4"). The
  A-115 semantics carry: changes apply live, Done saves, Esc leaves
  without saving.
- **Mute toggle is the new eighth key** (`muted`, default `false`):
  add it to the `Settings` struct, `SETTING_KEYS`, `to_text`, the parser,
  `adjust_setting` (inserted after `master_volume`: row 5 becomes mute,
  fullscreen/debug_overlay shift to 6/7, and the Done row shifts to 8 —
  the `SETTING_KEYS` order is the settings screen's row order), and the
  settings screen's rendered rows. Mute beats volume: muted means no
  playback (or volume 0 at the sink — pick one, log it, test it).
  Every existing config test that counts keys or pins row indices gets
  updated in the same commit.
- **Rate limiting:** a per-cue cooldown (the same cue inside ~50–100 ms
  drops, different cues independent) or a global cues-per-second cap —
  pick the shape that best answers the plan's "many attacks per tick
  must not become noise", log it, and make it **pure and testable**
  (a small struct fed a cue + a timestamp, returning play/drop). It
  lives client-side in the new module; the client is exempt from the
  determinism source bans (`Instant` is fine there), but the limiter
  must sit between the cue source and the sink — the sim's event flow
  and the goldens never see it.

## 6. Traps — read twice, these are the ways this phase goes wrong

- **T1 — Goldens are the project's heartbeat.** demo `0xb6fff6659cfb7709`,
  flagship `0x6e9a18bd7c5f699f`, content `0x9bc18c521107b262` (tick-0
  `0x71a924ad5799e4b3`, map id `0xd38136401ab02ff1`). Any movement = revert.
  Audio should not even be able to move them (the sink is fed after the
  step and feeds nothing back — FD-9, stated in `audio.rs`'s own header);
  a surprise movement means you broke the boundary or fed the sink from
  inside the sim.
- **T2 — The sink stays presentation-side.** `on_events` is called after
  `step()`, never from inside it; nothing the sink does may be observable
  by the simulation; no sim code may call into audio. The M9 posture,
  kept.
- **T3 — Dropping the rodio `OutputStream` silences everything.** Store
  the stream with the sink for the `App`'s lifetime. If sound works for
  one frame then stops — this is it.
- **T4 — Never block or crash the loop.** Device probing once at startup;
  per-cue work is a pre-built source handed to the mixer; `on_events`
  must not allocate per event beyond what the rate limiter needs. A
  device that vanishes mid-session (USB unplug) must not panic the app —
  degrade to null and say so in the evidence line.
- **T5 — The machine cannot hear.** The verification environment (Xvfb,
  no audio stack) has no sound device — so every windowed run there
  exercises the null fallback, which is exactly §4.3's machine half:
  cue flow counted, no crash, honest summary lines. The audible half —
  "does each of the nine moments sound distinct and right" — is the
  owner's re-test, the DEBT-008 pattern. Do not claim sounds are good;
  claim they are wired, distinct by construction, and counted.
- **T6 — The embedded font is an ASCII subset** (`client/src/text.rs`).
  Any on-screen audio labels (volume value, mute row) are ASCII only.
- **T7 — The settings screen grew.** The new mute row shifts focus
  indices: `SETTING_KEYS`, `adjust_setting`'s match arms, the rendered
  rows, and the `ui.rs` button-id↔focus-index tests move together in one
  commit. Keyboard AND mouse must both reach the new row.
- **T8 — XTEST driver discipline (the Phase 3 lesson).** Keys sent faster
  than ~0.3 s apart can be processed against stale screen state under
  llvmpipe load; pass mode-specific CLI args BEFORE `Popen`; verify the
  evidence lines (the startup line says where the settings came from;
  the smoke line reports the session honestly). Use ≥0.25–0.4 s per key.
- **T9 — This execution environment kills background processes** between
  tool calls (setsid/nohup silently die). Run every build and every Xvfb
  session in the foreground; long builds need generous explicit timeouts.
  Keep a work log per the multi-agent protocol you were given
  (`/home/z/my-project/worklog.md`, append-only) if you are operating
  under that harness.
- **T10 — Keep the smoke honest.** The `--frames` evidence line
  (`main.rs:2846`) should now also say what audio did: null fallback vs
  active sink, cues voiced vs dropped by the limiter. A menu-only run
  reports no cues. Never print "audio ok" where you did not verify
  anything.
- **T11 — The plan expects many small commits** — one logical change
  each, gate-green each. If a commit's message needs "and", split it.
