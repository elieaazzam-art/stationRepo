## 1. Mission

Implement **Phase 3 — Menu and Settings** of milestone M10.2, exactly as
specified in `docs/PLAN-M10.2.md` §3. The goal: **a proper start flow instead
of dropping straight into a match.**

The six work packages (the plan's own numbering — they are your scope law):

- **§3.1 Application state machine** — client-side:
  `MainMenu -> (Settings | NewMatch) -> InMatch -> (PauseMenu | EndScreen) -> MainMenu`.
  Pure data and transitions, unit-tested. Nothing here touches the sim.
- **§3.2 Main menu** — New Match, Settings, Quit.
- **§3.3 New Match screen** — Mode (Player vs AI / AI vs AI spectate /
  Sandbox no-opponent), Seed (random by default, editable — reuses the
  existing `--seed` path), Map (the existing Crossroads, listed from the
  bundle — `ContentBundle::maps` is already a `Vec<MapDef>` with one entry),
  Start button. Starting a match reuses the existing drop + reconstruct path
  (A-014/A15 style), so determinism is unchanged.
- **§3.4 Settings** — edge scroll on/off, scroll speed, camera zoom limits,
  master volume (Phase 4 placeholder), fullscreen toggle, show debug overlay
  by default. Persist to a small config file in the user config directory
  using a simple hand-written `key=value` format (no serde in the client
  path — it is not on the client's allow-list). Load with safe defaults when
  the file is missing or malformed.
- **§3.5 Pause menu** — Esc during a match opens Resume, Settings, Restart,
  Quit to Menu. The match pauses through the existing `MatchHost` pause.
- **§3.6 UI implementation** — reuse the existing fontdue text renderer and
  UI overlay pass. Buttons are plain rectangles with hover states. Keep it
  keyboard AND mouse navigable.

**Exit (plan's own words, verbatim):** the game starts at the menu, a match
can be started in each mode, settings persist across runs, and tests cover
the state machine and config parser (including corrupt files).

## 5. Work packages with the concrete anchors (all verified at the base commit)

### 5.1 §3.1 — the state machine (start here; it is pure and testable)

Build it as a **new pure module** — follow the Phase 2 precedent of
`client/src/silhouette.rs` and `client/src/report.rs`: a self-contained file
with its unit tests in a `#[cfg(test)] mod`, and thin wiring in `main.rs`.
Suggested name: `client/src/screens.rs` (or `menu.rs`). DEBT-013 documents
that `main.rs` (2358 lines) and `render.rs` (2691 lines) are known monoliths
whose split is scheduled post-Alpha — so ADD a clean module rather than
growing the monolith, and keep your wiring layer thin.

- Enum of screens: `MainMenu`, `Settings { return_to }`, `NewMatch`,
  `InMatch`, `PauseMenu`, `EndScreen { outcome }` — with pure transition
  functions (`fn on_confirm(state, ...)`, `fn on_back(state, ...)`,
  `fn on_key(state, key, ...)`) that return `(new_state, effect)` pairs.
  Effects are an enum the app layer interprets (`StartMatch { mode, seed,
  map_id }`, `Resume`, `RestartMatch`, `QuitApp`, ...). No winit types inside
  the pure module — plain enums only — so tests need no window.
- Every transition edge from the plan's diagram gets a test, including the
  awkward ones: Settings must remember where it was opened from (main menu vs
  pause menu) and return there; EndScreen offers menu + restart; Esc inside
  the pause menu returns to InMatch (paused state decision logged, §5.5).
- Keyboard navigation is part of the pure machine: up/down moves focus
  within the focused screen's button list (wrapping is fine — log it),
  Enter activates, Esc backs out. Mouse hover also moves focus. One pure
  `focus_next(...) / focus_prev(...) / activate_focused(...)` set with tests.

### 5.2 §3.2 — main menu + §3.3 — New Match screen

Reuse `client/src/ui.rs`'s `Button` (it already has `contains()` hit-testing)
and the existing overlay pass in `render.rs`. Buttons are plain rectangles
with a hover state and a focus ring for keyboard users. All labels are ASCII
— see §6 trap T8 (the embedded font is an ASCII-only subset of DejaVu Sans).

- **New Match screen fields:**
  - Mode: Player vs AI / AI vs AI (spectate) / Sandbox. This maps onto the
    host construction seam — see below.
  - Seed: u64, **random by default** (the plan says random; there is no
    approved RNG for UI purposes — use a seed from the OS entropy source
    available in std, log it as an assumption, and never let it touch the
    sim's deterministic RNG), editable. The `--seed` CLI arg (parser at
    `main.rs::seed_from_args`, default 7) pre-fills the field so every
    existing reproducibility affordance keeps working.
  - Map: list from `bundle.maps` (`ContentBundle::maps: Vec<MapDef>`,
    lookup by id via `ContentBundle::map(&self, id)`). Exactly one authored
    map (Crossroads) exists; render the list generically so more maps need
    no code change.
  - Start button → effect `StartMatch { mode, seed, map_id }`.
- **The host construction seam (the real work):** today `App::new`
  (`main.rs:317`) builds the match host immediately, and `build_host`
  (`main.rs:413-423`) hard-wires exactly one controller — P1 Human + one
  `alpha_controller(bundle, &world, AI, setup.seed)` for P2 via
  `MatchHost::with_controllers`. The match setup carries
  `controller: ControllerKind::Human` / `ControllerKind::Ai`
  (`main.rs:322-327`). Your changes:
  - **Defer host construction**: `App::new` must no longer build the host;
    the window/renderer start, the main menu shows, and the host is built
    when Start is pressed (or when a restart/end-screen rematch happens).
    Everything that assumed a host exists from frame 0 (HUD, minimap,
    tooltips, F8, `--record`) must guard on "match active". Keep the
    `--frames N` smoke honest: at the menu there are no sim commands and
    the summary prints the menu state — see trap T7.
  - **Mode mapping** (log as an assumption; the plan names the modes but
    not their controller semantics):
    - Player vs AI = exactly today's wiring (P1 Human + P2 `alpha_controller`).
    - AI vs AI (spectate) = `alpha_controller` for BOTH players; the human
      input path must not submit sim commands (the purest place is to make
      the orders layer a no-op when spectating — log it; refusal cues are
      unnecessary noise in spectate, decide and document one way).
    - Sandbox = P1 Human, **P2 present in the setup but controller-less**
      (an empty controllers vec or omitting P2 from the vec — whichever
      `MatchHost::with_controllers` accepts; P2's starting force sits idle,
      which is exactly the "no opponent, for testing" the plan wants).
  - **Restart** (`main.rs:426`, the A15 drop + reconstruct) and the pause
    menu's Restart both rebuild through the same mode/seed/map record —
    a same-seed restart reproduces the same match (that guarantee is
    already test-pinned; do not weaken it).

### 5.3 §3.5 — pause menu and the EndScreen promotion

- The **EndScreen** already exists as a rendered panel (`main.rs:2114`,
  "VICTORY/DEFEAT/MUTUAL DESTRUCTION" + restart-R). Promote it into the
  state machine (`EndScreen` state) and add the two buttons the plan's
  diagram implies: back to menu (drops the host) and restart.
- **The pause menu pauses through the existing MatchHost pause**:
  `host.set_paused(!host.is_paused())` (`main.rs:1310`, bound to P today).
  Decide and log: does opening the pause menu force-pause and restore the
  prior pause state on resume, or does it simply behave like P? Pick the
  one that keeps P working exactly as re-tested in Phase 1.
- **Esc ladder rework — the sharpest integration point in this phase.**
  `input::escape_action(armed, placing, selection_nonempty)` (`input.rs:275`)
  currently ends with `EscapeAction::Quit => event_loop.exit()`
  (`main.rs:1393`) — Esc-Esc-Esc-quits the app mid-match. The plan now says
  Esc during a match opens the pause menu. Make the ladder's final rung
  return a new `EscapeAction::OpenPauseMenu` instead of `Quit`, update the
  rung tests (`input.rs:622-631` — the `escape_action(false,false,false)`
  assertion changes), and update the README controls card + PLAYTEST
  controls card in the same commit. The earlier rungs (cancel armed →
  cancel placement → clear selection) stay exactly as Phase 1 re-tested
  them; only the exhausted-ladder behavior changes, and the owner must be
  able to see that in the card.

### 5.4 §3.4 — settings and the config file

The six settings keys (plan's list — do not invent more):

| key (suggested) | default | wired to |
|---|---|---|
| `edge_scroll` | `true` | **already wired**: `edge_scroll_enabled` (`main.rs:222`, hard-`true` at `main.rs:384`, read at `main.rs:1464-1466`). Flipping it from settings is the **DEBT-014 repayment** — mark the row repaid in the same commit. No input-path change needed |
| `pan_speed` | `34.0` | `PAN_TILES_PER_SECOND` (`main.rs:68`, currently a const shared by keys + edge band) — make the value come from config |

Lowest-risk approach: apply the user limits as an additional clamp on `camera.distance` in the client after every zoom/`adjust_pitch`-style call — no engine change, presentation-only. If you must touch the engine instead, keep it data-only and golden-safe; the Phase 2 ground-palette commit is the precedent for an allowed engine touch |
| `master_volume` | `1.0` | Phase 4 placeholder: stored, loaded, persisted, shown on the settings screen; nothing audible consumes it yet (the `AudioSink` seam is fed but null-backed — DEBT-011). Note this on the screen if trivially possible |
| `fullscreen` | `false` | winit: `window.set_fullscreen(...)` at toggle and applied after window creation at startup. | `debug_overlay` | `false` | F3 overlay default visibility at match start |

- **The config file** — a new pure module (e.g. `client/src/config.rs`)
  with unit tests: a hand-written `key=value` text format, one key per line,
  `#` comments, unknown keys ignored, missing/malformed file or value →
  **safe defaults for the whole file** (the plan's letter; per-key salvage is
  a nicer behavior — if you implement it, log the choice as an assumption
  and test it). Round-trip test: save then load equals the same settings.
  Corrupt-file tests are an explicit plan exit item.
- **The config directory — NO new crates.** The client allow-list
  (`tests/architecture_law.rs:119`, `allowed_external()`) already lists
  more than the manifest uses (anyhow, bytemuck, cpal, egui, fontdue, glam,
  image, pollster, thiserror, wgpu, winit) but NOT `dirs`, NOT `serde`.
  Adding `dirs` = allow-list edit + ADR + the plan's "prefer no new crates"
  — so resolve the config dir by hand from std env:
  - Windows: `%APPDATA%\pandemonium\settings.cfg`
  - macOS: `$HOME/Library/Application Support/pandemonium/settings.cfg`
  - Linux/BSD: `$XDG_CONFIG_HOME/pandemonium/settings.cfg`, else
    `$HOME/.config/pandemonium/settings.cfg`
  - No HOME/APPDATA at all (CI, containers): fall back to in-memory defaults
    with persistence silently disabled — never panic, never crash the loop
    (same spirit as PLAN §4.3's audio fallback). Log all of this as an
    assumption.
- Save timing: write on leaving the settings screen (OK/Apply) — pick one,
  document it in the screen itself if you add an Apply button, log the
  choice. Test the write path as a pure "settings → string" function plus a
  thin `std::fs` wrapper.

### 5.5 §3.6 — UI implementation

- Reuse the fontdue atlas (`client/src/text.rs`) and the existing
  screen-space UI overlay pass in `render.rs` — the bottom bar, tooltips,
  and info panel already render through it; menus are more of the same
  (solid panels, bordered buttons, one accent color for hover/focus —
  reuse the blue/orange palette constants so nothing new is invented).
- Every menu screen is keyboard AND mouse navigable (plan's own exit bar):
  hover sets focus, click activates, arrows + Enter work alone.

  way so Quit writes a pending `--record`.)

## 6. Traps — read twice, these are the ways this phase goes wrong

- **T1 — Goldens are the project's heartbeat.** demo `0xb6fff6659cfb7709`,
  flagship `0x6e9a18bd7c5f699f`, content `0x9bc18c521107b262` (tick-0
  `0x71a924ad5799e4b3`, map id `0xd38136401ab02ff1`). Any movement = revert.
  Menu work should not even be able to move them (nothing above the sim
  boundary), which is exactly why a surprise movement means you broke the
  boundary.
- **T2 — The Escape ladder is re-tested, shipped behavior.** Only its final
  rung changes (Quit → OpenPauseMenu). Rerun the ladder tests, update both
  control cards (README + PLAYTEST) in the same commit.
- **T3 — Deferred host construction ripples.** HUD assembly, minimap,
  tooltips, F8 dump, `--record`, the end screen, restart-R, the feedback
  clock — everything touches the host. Grep `self.host` / `host.` and guard
  each site on "match active". A menu-only session must never panic, never
  write a report, never submit a command.
- **T4 — Spectate must actually silence human orders.** If you only hide
  the command card but leave the input path live, right-clicks will inject
  P1 commands into a match the "player" does not own. Kill it at the orders
  layer and pin it with a test.
- **T5 — Sandbox still needs a legal 2-player setup.** The sim's match
  rules (defeat = zero owned Footprint structures, M8) and the spawn/
  population paths assume both players exist. Controller-less P2 is fine;
  a missing P2 from the setup is not. Pin a test that a sandbox match
  constructs, ticks, and (if the player idles) eventually resolves with
  P2's base standing — a short one, no golden, just invariants.
- **T6 — No new crates, no serde.** The architecture-law test scans every
  manifest and the source-scan tests are strict. Config parsing is
  hand-rolled `key=value`; config dir is env-var resolution. `std::env`,
  `std::fs`, `std::time` are all fine (client is exempt from the
  determinism source bans).
- **T7 — Menu-first changes the meaning of the smoke runs.** `--frames N`
  now ends at the menu unless the run navigates. The CI job that runs
  `cargo run -p pandemonium-client` is safe (no display → the headless
  smoke fallback at `main.rs:85-101`), but your Xvfb verification must
  XTEST-navigate: menu → New Match → Start → the match renders and
  responds; that IS the machine-half of the phase exit. Also update
  `docs/PLAYTEST.md`'s per-OS quickstart (§1) — it currently documents
  launching straight into a match.
- **T8 — The embedded font is an ASCII subset of DejaVu Sans**
  (`text.rs:8`). All menu labels must be ASCII. Lowercase and digits are
  covered (full ASCII range is rasterized), but if you see boxes in the
  Xvfb captures, you wrote a non-ASCII character — fix the label, not the
  font.
- **T9 — Xvfb has no window manager.** Fullscreen toggling may be a no-op
  or misbehave there. Machine-verify what you can, be honest in the notes
  about what only the owner's display can prove, and log it (the DEBT-008
  recipe in `docs/DEBT.md` is the standing env recipe: Xvfb screen at least
  1280x800, userland libEGL/libGLESv2 + glvnd `__EGL_VENDOR_LIBRARY_DIRS`,
  `WGPU_BACKEND=gl`, XTEST via userland libXtst, keyboard focus via
  `xdotool windowfocus`, and NO WM running).
- **T10 — This execution environment kills background processes** between
  tool calls (setsid/nohup silently die). Run every build and every Xvfb
  session in the foreground; long builds need generous explicit timeouts.
  Keep a work log per the multi-agent protocol you were given
  (`/home/z/my-project/worklog.md`, append-only) if you are operating under
  that harness.
- **T11 — The plan expects many small commits** — one logical change each,
  gate-green each. If a commit's message needs "and", split it.
